# Wedding import

`../migrate_weddings.sql` imports `real_meeter.weddings` and `real_meeter.wedding_guest` into `vibecoded_meeter`, confirmed by the user on MariaDB 12.3.3. The script explicitly selects that destination and qualifies its temporary stored procedure with that schema. It is a manual personal-data import, never a Flyway migration, and does not change the source database.

## Running

1. Stop the backend and all other writers. Back up the destination database and photos with the correct environment, using `../backup.ps1` or your normal backup tool.
2. Verify that existing destination people/place IDs still identify the original source people/places. The script validates references exist, but cannot establish identity from an ID alone. People and places must already have been imported.
3. In phpMyAdmin, select **vibecoded_meeter**, then use Import to run the entire updated `migrate_weddings.sql` file. Run from a clean session: routine DDL can implicitly commit an existing transaction. The procedure also checks its destination schema before creating the ledger. The account set immediately before CALL defaults to `pszkudlarek`; change that login if necessary. CALL and the final verification joins explicitly qualify `vibecoded_meeter`, so a client-side default schema cannot redirect them to `real_meeter`. Keep the SET and CALL together when manually retrying an existing procedure.
4. Check `destination_database`, `imported_weddings`, `imported_participant_links`, and the final `missing_weddings` (must be zero). Retain the ledger permanently. Run in a client that stops on errors; do not run isolated INSERT statements.

Requires the current MariaDB application schema, InnoDB tables, SELECT access to the source, and destination SELECT/INSERT/CREATE/CREATE TEMPORARY TABLES/CREATE ROUTINE/ALTER ROUTINE/EXECUTE permissions. The script uses a conventional `CREATE PROCEDURE ... BEGIN ... END`, followed by CALL and DROP PROCEDURE, with DELIMITER support. It does not use `BEGIN NOT ATOMIC`, which the installed phpMyAdmin analyzer rejects. A new ledger uses CHAR(36) for UUID text to avoid another analyzer warning; an existing native-UUID ledger is retained unchanged. Ledger and routine DDL precede the explicit data transaction because MariaDB DDL implicitly commits. A failure can leave an empty ledger and procedure, but wedding data and ledger rows roll back together. No application migration or server startup is performed by this script.

## Mapping

| Source | Destination |
| --- | --- |
| `weddings.id` | Persistent ledger source ID; fresh interaction ID and UUID |
| `info_after_hover` | Trimmed `interactions.name`; NULL/blank falls back to `Wesele #ID`. Nonblank names outside 2–128 characters stop the import. Original text remains in the ledger. |
| `date` | Both `interactions.start_date` and `end_date`, unchanged local timestamp |
| `description` | `interactions.long_desc`, unchanged including NULL |
| `man_id`, `woman_id` | `weddings.groom_id`, `bride_id`, and participant links |
| `wedding_place_id` | `weddings.ceremony_place_id` |
| `party_place_id`, `hotel_id` | Corresponding destination wedding fields |
| `poprawiny` | `weddings.had_after` |
| `was_i_invited` | `weddings.was_i_invited`, copied exactly (must be 0 or 1) |
| `wedding_guest.guest_id` | Deduplicated participant links |
| `partner_id` | Ledger `source_partner_id`; not automatically interpreted as a guest |

The importing account's linked Human is additionally included only for `was_i_invited=1`. Explicit source guest links and spouse references remain authoritative even when that flag is false. No invitation is inferred from guest membership, clique IDs or the existence of a source wedding. Relationship IDs are generated by the destination; their timestamp is the UTC import time and their creator is the importing account. These are migration metadata, not recovered historical audit records.

Missing people/places, orphan guest links, invalid dates/flags, identical spouses and an inconsistent ledger stop the import. Existing destination weddings with the same creator, couple and date but no ledger entry also stop it for manual inspection rather than being silently duplicated or merged. `partner_id` is retained without inventing guest semantics. The user confirmed that `info_after_hover` contains the wedding name. Missing source fields are not invented; SQL errors roll back the data transaction.

## Correcting names from the earlier import

After backup and backend shutdown, run the entire `../fix_wedding_names.sql` file. It uses `migration_real_meeter_weddings.source_info_after_hover`, already copied during the initial import, so no access to `real_meeter` is needed. It changes only exact generated `Wesele #ID` names on ledger-linked weddings. Manually edited titles, other interactions, IDs, UUIDs, owners, dates and relationship metadata are preserved. It inserts no records and is repeatable. Blank original names retain the fallback. Nonblank names outside the application's 2–128 character limit are left unchanged and reported by `invalid_source_name_lengths`; they require an explicit naming decision rather than silent truncation. Re-running the main import alone does not rename existing weddings.

## Repetition and verification limits

Reruns skip source IDs already recorded in the ledger, preserve application edits and participant removals, and append newly added source weddings. They do not synchronize changed source records. A database-specific advisory lock serializes this script but does not replace stopping other writers. Do not drop the ledger to retry an import, and do not clear foreign-key checks.

The script was prepared from source column metadata and destination/server information supplied by the user and the application's versioned schema. The extracted procedure has been checked with the installed phpMyAdmin SQL parser. That parser does not fully support schema-qualified CALL syntax: it may display analysis warnings for the qualified call even though MariaDB supports it. Do not remove its database qualifier to silence those warnings. Distinguish analyzer warnings from an actual numbered server error. The script has not been executed against source or application data. Review and test it on restored copies before the first import. If the earlier anonymous-block version actually completed despite analyzer warnings, the same ledger prevents a second import; do not delete it.

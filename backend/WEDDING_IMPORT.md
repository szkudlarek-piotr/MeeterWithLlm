# Wedding import

`../migrate_weddings.sql` imports `real_meeter.weddings` and `real_meeter.wedding_guest` into `vibecoded_meeter`, the destination confirmed by the user on MariaDB 12.3.3. The script explicitly selects that destination and qualifies its temporary stored procedure with that schema. It is a manual import of personal data, never a Flyway migration, and it does not change the source database.

## Running

1. Stop the backend and all other writers. Back up the destination database and photos with the correct environment, using `../backup.ps1` or your usual backup tool.
2. Check that the existing destination people and place IDs still identify the original source people and places. The script validates that references exist, but it cannot establish identity from an ID alone. People and places must already have been imported.
3. In phpMyAdmin, select **vibecoded_meeter**, then use Import to run the entire updated `migrate_weddings.sql` file. Run it from a clean session: routine DDL can implicitly commit an existing transaction. The procedure also checks its destination schema before creating the ledger. The account set immediately before CALL defaults to `pszkudlarek`; change that login if necessary. CALL and the final verification joins explicitly qualify `vibecoded_meeter`, so a client-side default schema cannot redirect them to `real_meeter`. When manually retrying an existing procedure, keep the SET and CALL together.
4. Check `destination_database`, `imported_weddings`, `imported_participant_links` and the final `missing_weddings` (which must be zero). Keep the ledger permanently. Run it in a client that stops on errors; do not run isolated INSERT statements.

It requires the current MariaDB application schema, InnoDB tables, SELECT access to the source, and destination SELECT, INSERT, CREATE, CREATE TEMPORARY TABLES, CREATE ROUTINE, ALTER ROUTINE and EXECUTE permissions. The script uses a conventional `CREATE PROCEDURE ... BEGIN ... END`, followed by CALL and DROP PROCEDURE, with DELIMITER support. It does not use `BEGIN NOT ATOMIC`, which the installed phpMyAdmin analyser rejects. A new ledger uses CHAR(36) for UUID text to avoid another analyser warning; an existing ledger with a native UUID type is kept unchanged. The ledger and routine DDL come before the explicit data transaction, because MariaDB DDL commits implicitly. A failure can leave an empty ledger and procedure, but the wedding data and ledger rows roll back together. No application migration or server start is performed by this script.

## Mapping

| Source | Destination |
| --- | --- |
| `weddings.id` | Persistent ledger source ID; a fresh interaction ID and UUID |
| `info_after_hover` | Trimmed `interactions.name`; NULL or blank falls back to `Wesele #ID`. Non-blank names outside 2–128 characters stop the import. The original text remains in the ledger. |
| `date` | Both `interactions.start_date` and `end_date`, unchanged local timestamp |
| `description` | `interactions.long_desc`, unchanged, including NULL |
| `man_id`, `woman_id` | `weddings.groom_id`, `bride_id` and the participant links |
| `wedding_place_id` | `weddings.ceremony_place_id` |
| `party_place_id`, `hotel_id` | The corresponding destination wedding fields |
| `poprawiny` | `weddings.had_after` |
| `was_i_invited` | `weddings.was_i_invited`, copied exactly (must be 0 or 1) |
| `wedding_guest.guest_id` | Deduplicated participant links |
| `partner_id` | Ledger `source_partner_id`; not automatically interpreted as a guest |

The importing account's linked Human is additionally included only for `was_i_invited=1`. Explicit guest links and spouse references from the source remain authoritative even when that flag is false. No invitation is inferred from guest membership, clique IDs or the mere existence of a source wedding. Relationship IDs are generated by the destination; their timestamp is the UTC import time and their creator is the importing account. These are migration metadata, not recovered historical audit records.

Missing people or places, orphaned guest links, invalid dates or flags, identical spouses and an inconsistent ledger stop the import. Existing destination weddings with the same creator, couple and date but no ledger entry also stop it for manual inspection, rather than being silently duplicated or merged. `partner_id` is kept without inventing guest semantics. The user confirmed that `info_after_hover` contains the wedding name. Missing source fields are not invented; SQL errors roll back the data transaction.

## Correcting names from the earlier import

After a backup and a backend shutdown, run the whole `../fix_wedding_names.sql` file. It uses `migration_real_meeter_weddings.source_info_after_hover`, which was copied during the initial import, so it needs no access to `real_meeter`. It changes only exact generated `Wesele #ID` names on ledger-linked weddings. Manually edited titles, other interactions, IDs, UUIDs, owners, dates and relationship metadata are preserved. It inserts no records and can be repeated. Blank original names keep the fallback. Non-blank names outside the application's 2–128 character limit are left unchanged and reported by `invalid_source_name_lengths`; they need an explicit naming decision rather than silent truncation. Re-running the main import alone does not rename existing weddings.

## Repetition and verification limits

Re-runs skip source IDs already recorded in the ledger, keep application edits and participant removals, and add newly appearing source weddings. They do not synchronise changed source records. A database-specific advisory lock serialises this script but does not replace stopping other writers. Do not drop the ledger to retry an import, and do not disable foreign-key checks.

The script was prepared from the source column metadata and from the destination and server information supplied by the user, together with the application's versioned schema. The extracted procedure has been checked with the installed phpMyAdmin SQL parser. That parser does not fully support schema-qualified CALL syntax: it may show analysis warnings for the qualified call even though MariaDB supports it. Do not remove the database qualifier to silence those warnings. Distinguish analyser warnings from an actual numbered server error. The script has not been run against source or application data. Review and test it on restored copies before the first import. If the earlier anonymous-block version actually completed despite analyser warnings, the same ledger prevents a second import; do not delete it.
